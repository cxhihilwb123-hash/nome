# Nome iOS v6.5.6 real-core and physical-device execution plan

Date: 2026-07-21
Status: Phase 0 complete; no real-core installation authorized by this plan

## 1. Problem statement

The Nome iOS product overlay and light/dark preview smoke pass are already
implemented and locally checkpointed. The remaining functional claim is
blocked by the runtime boundary: `apps/ios/Libraries/sim` still contains the
small preview core, `apps/ios/Libraries/ios` is absent, and the local downloaded
core artifacts report SimpleX `6.5.5.0` while the current checkout and Xcode
references report `6.5.6.1` / marketing version `6.5.6`.

The same machine is currently being used for Android testing. iOS work must
therefore remain in `/Users/forkman03/project/nome/simplex-chat-ios`, preserve
the dirty Android worktree at `/Users/forkman03/project/nome/simplex-chat`, and
avoid heavy Xcode builds while Android timing-sensitive tests are running.

This plan must determine the next truthful, executable iOS batch without
mistaking a preview core, a version-mismatched artifact, an offline device, or a
generic build for real v6.5.6 functional proof.

## 2. Solution summary

Execute a gated sequence:

1. Produce a lightweight, read-only Phase 0 packet covering repository state,
   installed libraries, local artifact version/architecture, build tools,
   Xcode destinations, and physical-device availability.
2. Classify the available routes as `READY`, `COMPATIBILITY_CANDIDATE`, or
   `BLOCKED` using explicit version, architecture, provenance, and device gates.
3. Do not run any library replacement, signing, installation, or heavy build
   unless one route meets every prerequisite and Android testing is no longer
   timing-sensitive.
4. If no exact real-core route is ready, keep the current preview simulator
   intact and move the next independent iOS batch to Dynamic Type and
   accessibility verification instead of weakening the real-core acceptance
   criteria.

No remote push, release-identifier migration, signing change, App Group change,
or Android edit is part of this plan.

## 3. Detailed technical design

### 3.1 Documentation and runtime boundary

The relevant iOS architecture is documented in
`apps/ios/spec/architecture.md` and `apps/ios/spec/api.md`: all user actions
cross the Swift-to-Haskell FFI bridge before reaching the protocol/database
core. `apps/ios/spec/impact.md` marks that bridge as affecting every product
concept. A preview-only FFI implementation can validate navigation and visual
states, but it cannot prove invitations, addresses, groups, persistence, or
two-account messaging.

Phase 0 changes only plan/evidence text. It does not change source behavior, so
no product/spec behavior update is required. Any later library or project-file
change must be planned as a separate implementation batch and re-run the
three-layer impact review first.

### 3.2 Route classification

#### Route A: Apple Silicon simulator

`READY` requires all of the following:

- a production-sized, marker-free simulator core supporting the architecture
  exposed by the installed Xcode simulator destination;
- exact compatibility with the current SimpleX `6.5.6.1` checkout and Xcode
  archive references, or documented authoritative provenance proving the same
  source revision;
- a staged packet that passes the read-only source and preflight checks before
  any `--prepare` action.

The current x86_64 `6.5.5.0` simulator artifact cannot satisfy this route on an
arm64 simulator and cannot be treated as a v6.5.6 result.

#### Route B: physical iPhone/iPad

`READY` requires all of the following:

- a connected, unlocked, trusted iPhone/iPad visible to full Xcode;
- an arm64 device artifact with authoritative provenance and exact
  `6.5.6.1` compatibility;
- configured signing/bundle settings sufficient for a device build;
- dry-run checks passing before the guarded device-only preparation command.

A production-sized `6.5.5.0` arm64 artifact is only a
`COMPATIBILITY_CANDIDATE`; it may be studied or staged read-only, but it cannot
close the v6.5.6 real-core gate.

#### Route C: local build

`READY` requires the repository-supported Nix environment, sufficient disk
space, the exact checked-out source revision, and a reproducible artifact
packet. Installing Nix or starting a local core build is outside Phase 0 and
must be separately reviewed because it can consume substantial time, disk, and
machine resources.

### 3.3 Safety invariants

- Never invoke `scripts/ios/prepare-device-real-core.sh --prepare`,
  `scripts/ios/run-real-core-batch0.sh --prepare`, `scripts/ios/prepare.sh`, or
  `scripts/ios/prepare-x86_64.sh` in Phase 0.
- Never replace `apps/ios/Libraries/sim` or create
  `apps/ios/Libraries/ios` from a version-mismatched candidate.
- Never synchronize `SimpleX.xcodeproj/project.pbxproj` to candidate filenames
  until the matching real-core route is approved for implementation.
- Keep all generated large/binary artifacts outside Git. Track only small text
  evidence required to resume the decision.
- Preserve both Android HEAD and its existing tracked/untracked changes; do not
  reset, clean, stash, stage, or edit the Android worktree.
- Do not push any branch or create any remote mutation.

### 3.4 Threat model

Assets at risk are message confidentiality, local database integrity, build
provenance, signing identity, and the user's concurrent Android work.

- A stale or tampered core artifact could expose incompatible FFI behavior or
  falsely appear functional. Mitigation: require authoritative provenance,
  exact version/revision, architecture inspection, production-size checks, and
  preview-marker scans before use.
- A device artifact installed into the simulator path, or the reverse, could
  produce misleading build/runtime results. Mitigation: keep simulator and
  `iphoneos` routes separate and use device-only guarded preparation.
- A physical device visible but locked, untrusted, or offline could be
  mistaken for an executable test target. Mitigation: require live full-Xcode
  visibility immediately before build/install.
- Signing or identifier edits made merely to obtain a build could silently
  alter Keychain, App Group, notification, or deep-link behavior. Mitigation:
  keep release identity outside this batch.
- Concurrent heavy iOS builds could distort Android performance tests.
  Mitigation: Phase 0 is read-only/lightweight; heavy work waits for a safe
  machine window.

## 4. Detailed implementation steps

### Phase 0: current-state packet

1. Record iOS branch, HEAD, and status; record Android branch, HEAD, tracked
   source paths, tracked diff digest, and a count/snapshot of untracked files
   without modifying them. Treat concurrent `.gradle-review` generation as
   Android-owned runtime activity rather than requiring a frozen untracked
   status.
2. Inventory `apps/ios/Libraries/sim` and `apps/ios/Libraries/ios`; record file
   sizes, architectures, preview markers, and archive names.
3. Inventory local `pkg-ios-*-swift-json` candidates and record their embedded
   version names, sizes, architectures, and marker results.
4. Check `nix`, `mac2ios`, full Xcode, available simulators, and connected or
   offline physical devices.
5. Run only the read-only repository checks:
   `check-real-core-sources.sh`, `check-real-core.sh`,
   `check-ios-simulator-real-core-route.sh`, and
   `check-ios-device-readiness.sh`.
6. Write a small evidence summary under
   `plans/evidence/20260721_nome_ios_real_core_phase0/` and verify that the only
   tracked Phase 0 additions are this plan and its text evidence.

### Phase 1 decision gate

1. If an exact `6.5.6.1` simulator artifact is available, stage it without
   `--prepare`, verify the staged packet, then create a separate reviewed plan
   for replacement/build/smoke.
2. If an exact `6.5.6.1` arm64 device artifact and a live trusted device are
   available, run the device preparation dry-run only, then create a separate
   reviewed plan for signing/build/install/functional QA.
3. If neither route is ready, leave the core untouched, document the blockers,
   and schedule the independent accessibility/Dynamic Type batch next.

### Later functional QA after a real route is ready

Run real one-time invitation, public address, group creation/joining,
two-account messaging, persistence/relaunch, notification/share-extension, and
final screenshot batches. These are intentionally not claimed or executed by
Phase 0.

## 5. Testable acceptance criteria

- The evidence states the exact iOS and Android HEADs, records the Android
  tracked diff digest before and after Phase 0, and confirms no Phase 0 command
  targeted an Android path. If the Android process changes its own tracked or
  untracked state concurrently, the evidence records the new digest/path set
  separately instead of overwriting, reverting, or claiming ownership of it.
- Installed preview libraries and local artifact candidates are each reported
  with version, size, architecture, and preview-marker status.
- Xcode device evidence distinguishes `connected`, `offline`, and `simulator`
  entries; a failed sandbox query is not interpreted as device absence.
- Each real-core route has a single explicit classification and blocking
  reason.
- No library directory, Xcode project, Swift/Haskell source, signing setting,
  bundle identifier, App Group, or Android file is changed.
- No heavy Xcode/Core build runs while Android testing is active.
- No remote is pushed.
- The plan passes two consecutive adversarial reviews with zero issues before
  any mutating implementation batch.

## 7. Adversarial plan review

### Review pass 1

Issue found and corrected: the original acceptance criterion required the
entire Android status digest to remain unchanged. Active Android tests are
currently generating `.gradle-review` files, so that criterion could falsely
attribute Android-owned runtime churn to iOS work. Phase 0 now compares tracked
source state separately and records untracked churn as concurrent external
activity. No other internal, documentation, security-boundary, or execution
issue was found.

### Review pass 2

ZERO_ISSUES. Required sections are present; referenced documents and scripts
exist; route gates keep exact-version, architecture, provenance, device, and
signing concerns separate; Phase 0 contains no mutating command; Android and
remote boundaries are explicit; the threat model matches the execution steps.

### Review pass 3

ZERO_ISSUES. A second consecutive review confirmed the plan remains internally
consistent after recording pass 2, all expected Phase 0 failures remain visible
as blockers, and the only current tracked addition is the plan itself.
