# Chinese-friendly fork launch plan

## Problem statement

We want to create an open-source, Chinese-friendly SimpleX-based communication tool. The goal is not to rewrite the SimpleX protocol or hide upstream provenance. The first useful version should reduce onboarding friction for Chinese-speaking users while preserving upstream security properties and keeping future rebases practical.

The local repository started as an empty Git repository and was initialized from `simplex-chat/simplex-chat` `stable` on 2026-07-07.

## Solution summary

Start with a conservative distribution layer:

- keep the Haskell core, cryptographic protocol, queue logic, database logic, and networking semantics unchanged;
- keep upstream license and trademark attribution visible;
- improve Chinese user guidance, onboarding wording, packaging notes, and self-hosting documentation first;
- only change app identifiers, display names, icons, and default server/operator configuration after a separate review of license, trademark, release, and compatibility impact;
- prefer small changes that can be rebased onto upstream `stable`.

This produces a credible open-source Chinese-friendly edition without taking over the hardest and riskiest security responsibilities on day one.

## Detailed technical design

### Scope boundaries

Safe first phase:

- documentation under `docs/lang/zh-Hans/`;
- fork notes under `plans/`;
- Chinese translation fixes in existing `zh-rCN`, `zh-Hans`, and Chinese metadata files;
- user-facing onboarding copy that explains invitations, addresses, backups, local database ownership, and self-hosted servers more clearly;
- build/release documentation that explains how the fork is derived from upstream and how to verify upstream release provenance.

Deferred phase:

- Android `applicationId` change from `chat.simplex.app`;
- iOS bundle identifier, app group, notification service, and share extension rename;
- desktop app name, `.desktop` metadata, app icons, and update channel;
- default SMP/XFTP server/operator presets;
- app icon and brand assets;
- release signing keys and reproducible build verification.

Out of scope unless explicitly reviewed:

- Haskell core protocol changes;
- encryption primitives or key negotiation changes;
- message queue semantics;
- database migrations that alter user data ownership or security properties;
- push notification trust model changes.

### Current code entry points

Multiplatform app:

- Android application id: `apps/multiplatform/android/build.gradle.kts`
- Android manifest and app resources: `apps/multiplatform/android/src/main/`
- shared Android/Desktop strings: `apps/multiplatform/common/src/commonMain/resources/MR/`
- Simplified Chinese strings: `apps/multiplatform/common/src/commonMain/resources/MR/zh-rCN/strings.xml`
- desktop package assets: `apps/multiplatform/desktop/src/jvmMain/resources/distribute/`

iOS app:

- Xcode project: `apps/ios/SimpleX.xcodeproj/project.pbxproj`
- iOS app strings: `apps/ios/zh-Hans.lproj/Localizable.strings`
- iOS InfoPlist strings: `apps/ios/zh-Hans.lproj/SimpleX--iOS--InfoPlist.strings`
- notification extension strings: `apps/ios/SimpleX NSE/zh-Hans.lproj/`

Store/listing metadata:

- Android metadata: `fastlane/metadata/android/en-US/`
- Chinese metadata is not currently present.

### Threat model for this fork

Users may assume a Chinese-friendly fork has the same privacy guarantees as upstream. Any hidden change to routing, push notifications, default servers, build signing, or app identifiers can weaken that trust. Therefore every fork-specific behavior must be documented, and security-sensitive defaults must remain upstream-compatible until independently reviewed.

Attackers to consider:

- malicious fork operator trying to route users through controlled servers;
- malicious third-party redistributor replacing binaries;
- confused users trusting unofficial builds without verifying provenance;
- future maintainers accidentally diverging from upstream security fixes.

Mitigations:

- preserve upstream source attribution and AGPL license;
- document every fork-specific default;
- avoid cryptographic/core changes in phase one;
- keep a clean upstream remote and small diff;
- publish source and build instructions with every binary.

## Detailed implementation steps

1. Import upstream `stable` and work on a fork branch.
2. Add this launch plan to record the boundary.
3. Add a Simplified Chinese quick-start document under `docs/lang/zh-Hans/`.
4. Audit existing Simplified Chinese app strings for onboarding, invitation links, backups, network/server wording, and safety warnings.
5. Add Chinese Android metadata only after deciding the fork name.
6. Decide the fork brand name and trademark-safe description.
7. Add brand/app-id changes in a separate plan after reviewing Android, iOS, desktop, notifications, app groups, and update channels.
8. Build at least one target locally before claiming the fork is runnable.
9. Keep a rebase checklist for pulling upstream `stable` security fixes.
