## 1. Problem statement

P13 is frozen, so the completion Goal now enters Milestone 1, Batch 1A. The official root already
opens and migrates the two local databases, publishes `DBMigrationResult`, gates onboarding and the
main shell, and refuses service/worker startup on non-`OK` database state. Its current presentation
is a blank splash, a generic progress page, or the shared legacy `DatabaseErrorView`.

P01 must replace only the Android presentation of those existing root branches. It must not change
database initialization, migration confirmation, file names, key derivation, deletion behavior,
database or archive format, service/worker gating, onboarding ownership, or any native/core
contract. In particular:

- `chatDbStatus == null` means no terminal database result exists; the one-second display delay is
  not a timeout. It is `Opening` only while no Android database-key read failure has been published.
- Android Keystore database-key reads have two distinct failure shapes. A missing alias returns
  null, so startup continues with an empty key and can produce terminal `ErrorNotADatabase`. A
  present alias with unreadable encrypted material throws before `chatMigrateInit` assigns
  `chatDbStatus`; `Core.kt` then clears its in-progress flags in `finally` and the root otherwise
  stays indefinitely at null status. P01 must publish a no-secret read class for both shapes and
  must also preserve whether `initialRandomDBPassphrase` is true. Neither shape may be called
  opening, timeout, corruption, or a manually recoverable key when the user never knew the random
  key.
- `dbMigrationInProgress == true` proves only an in-progress migration operation, not a stage or a
  percentage.
- `chatDbEncrypted == true` means a non-empty key was supplied; it does not prove that the database
  opened.
- `ErrorNotADatabase` cannot distinguish a wrong key from arbitrary database corruption.
- only explicit upgrade/downgrade confirmation, an alternate-key open, and the existing
  timestamp-matched two-file re-encryption backup have bounded recovery actions.
- generic restore, rollback, cancel, resume, startup timeout, “68%”, “validation complete”, “identity
  loaded”, and “messaging service restored” have no v6.5.6 truth source and remain absent.

The frozen P01 PNG is a visual direction, not a data contract. The batch preserves its calm,
security-focused hierarchy and central database motif while removing fabricated stages and
determinate progress.

## 4. Production route and ownership

### 4.1 Root dataflow

```text
Android process / Activity start
  -> SimplexApp.onCreate
  -> initChatControllerOnStart
  -> unchanged initChatController
  -> Android Keystore key lookup
       -> success: unchanged chatMigrateInit
       -> database-key read failure: no-secret Android process state, existing return/throw retained
  -> ChatModel {
       chatDbStatus,
       chatDbEncrypted,
       ctrlInitInProgress,
       dbMigrationInProgress,
       localUserCreated
     }
     + Android database-key read status {
         none,
         missing alias + initial-random Boolean,
         decrypt failure + initial-random Boolean
       }
  -> unchanged MainScreen root-priority conditions
  -> PlatformDatabaseRootRoute seam
  -> Android NomeDatabaseRootStateAdapter
  -> Nome P01 renderer
  -> exact existing open / migration-confirm / matched-backup action
  -> fresh ChatModel terminal result
  -> unchanged onboarding or main shell
```

The seam is invoked only inside the already-selected root branch. It is not a navigation owner,
does not overlay another branch, and does not change the priority:

1. device migration root;
2. database migration operation;
3. database opening/no terminal result;
4. database error/recovery;
5. encryption and first-user readiness;
6. onboarding/main shell;
7. authentication, calls, privacy, and system overlays.

The database-error renderer remains inside the existing `!unauthorized` condition in `App.kt`.
When local authentication owns the screen, P01 must expose no passphrase field, IME focus,
database detail, migration consent, backup action, or recovery control behind or through the auth
overlay. Moving the seam outside this guard is forbidden even if the numerical root order remains
unchanged.

Both platforms preserve the current shared selection timing. Before the existing one-second delay
selects the opening branch, the root continues to use its current blank/system splash path. Once
`showInitializationView == true` selects the existing opening branch, Android renders Nome P01 and
Desktop renders the legacy progress content. The delay is presentation timing only: it is not a
timeout, a database stage, or evidence that initialization started/failed.

### 4.3 Existing-action extraction

The shared legacy `DatabaseErrorView` currently owns the exact retry, key-save/open,
migration-confirmation, and matched-backup operations. Gate C may mechanically extract the minimum
internal action/eligibility helpers so Android and legacy presentation call the same operation:

- open with the current key policy;
- open once with an explicitly entered key without writing Keystore or preference material;
- save an explicitly entered key, then open;
- confirm `YesUp` for an explicit upgrade;
- confirm `YesUpDown` for an explicit downgrade;
- evaluate both `.bak` files against `encryptionStartedAt`;
- copy only that exact matched pair and clear `encryptionStartedAt` only after both copies complete.

The extraction separates low-level operations from legacy post-action alerts:

- a suspend open operation invokes the exact existing `initChatController` arguments and returns
  only the fresh terminal model subtype;
- the legacy wrapper keeps its current alert behavior and Desktop continues to call it;
- the Android P01 route calls the low-level operation directly and renders only its sanitized
  reducer result; it never calls `showErrorOnMigrationIfNeeded`;
- on a fresh `DBMigrationResult.OK`, the Android route invokes the existing
  `platform.androidChatStartedAfterBeingOff()` success hook exactly once for the accepted attempt
  before leaving P01. This preserves passphrase-notification cancellation and the existing
  `SERVICE` / `PERIODIC` / `OFF` background restart behavior without editing those owners;
- a typed pair-copy helper returns only success/failure; the legacy wrapper may retain its existing
  alert, while Android P01 never calls the raw `restoreDb` alert path.

This deliberately changes only Android P01 orchestration after a successful matched-pair copy.
Copy success enters `RestoredPairReadyToOpen`; it does not claim database success and does not open
automatically. The user must explicitly activate “Open restored local database,” which performs one
fresh existing open attempt. Only `DBMigrationResult.OK` leaves P01. Desktop remains copy-only
legacy behavior. This two-step Android sequence is authorized presentation/controller work, not a
new native command or rollback guarantee.

The extraction must preserve each current low-level argument and ordering. It must not change the
confirmation enum, automatic new-database cleanup, copy destinations, backup eligibility, or
database contents. Android post-action alerts, semantics, UI tree, screenshots, and stored evidence
must not contain raw SQL, JSON, paths, or stack traces. Existing protected `Core.kt` diagnostics are
not repeated by P01; any fixture Logcat retained as evidence is sanitized and records that boundary
explicitly.

Because the current two sequential file copies are not an atomic rollback mechanism, the UI calls
this “restore the matching pre-encryption local pair,” warns that it is a bounded local recovery,
and never promises generic rollback. Disposable fixture hashes must prove both successful-pair and
injected-failure behavior before this action can be marked complete.

`ErrorNotADatabase` copy says only that the database could not be opened with the available key. It
does not assert “wrong passphrase” or “corruption.” `ErrorSQL`, `Unknown`, and migration internals
are mapped to fixed bilingual user-safe copy; raw payloads remain outside semantics, UI tree,
screenshots, Logcat evidence, and the adapter.

The Android key-read failure has higher reducer priority than null-status `Opening`. When
`initialRandomDBPassphrase == true`, `StoredRandomKeyUnavailable` also has higher priority than
`ErrorNotADatabase` / `AlternateKeyRequired`; the terminal result must not expose a manual-key
action merely because the missing-alias path reached native open. For a user-supplied key, both
read-failure shapes return null, continue to terminal `ErrorNotADatabase`, and map to
`StoredManualKeyUnreadable`; no manual-key null-status variant exists. “Open once” passes the
entered key directly to `initChatController(useKey = enteredKey)` and does not call
`ksDatabasePassword.set` or mutate `storeDBPassphrase` / `initialRandomDBPassphrase`. “Save and
open” remains a separate explicit action with the existing persistence ordering. The process state
is cleared only by a
successful database-key decrypt, an explicit allowed manual/open-restored attempt generation, or
process teardown. It is never inferred from elapsed time or a null result alone.

## 6. Interaction, lifecycle, and security

### 6.1 Single-submit

Each user action gets one local attempt identity and an atomic idle/in-flight terminal gate.
Rapid activation, keyboard IME action, accessibility activation, and recomposition share that
gate. The UI also disables actions while `ctrlInitInProgress` or `dbMigrationInProgress` is true.

The database operation is process-owned and is not canceled on rotation/background. The Android
route re-derives its state from `ChatModel` after recreation. A stale local callback may clear only
its own attempt; it cannot announce success, replace a newer error, write a key, or navigate.
Success is branch disappearance after a fresh `OK`, never a local Boolean. The attempt owner calls
`platform.androidChatStartedAfterBeingOff()` once for that fresh `OK`; stale/replayed composition
cannot call it again.

The no-secret Android key-read status is process-local state, not a timer or saved preference. It
is published before a missing-alias return or decrypt-failure throw. The random-key throw branch may
end the core job with null `chatDbStatus`, while the random-key missing-alias branch may end at
`ErrorNotADatabase`; both render `StoredRandomKeyUnavailable`, never `Opening` or alternate-key
entry. Manual retry exists only for a user-supplied key, clears the old failure after allocating a
new attempt, passes the explicitly entered key directly to the existing open call, and does not
save/replace it until the user selects the existing save action.

Pure injected action tests are preferred. If exact real invocation counts cannot be proved without
observation, use only the `plans/20260718_01.md` §4.4 seam: attempt ID, action kind, lifecycle
phase, and terminal class; no key, filename, error payload, database content, user, or server.
Prefer host-side JDI/JDWP method-entry counting before adding source. Any source observer must be
debug/test-only and absent from release dex/resources/manifest/runtime.

### 6.2 Secret lifetime

- The passphrase is held only in an Android composable `remember` value, never `rememberSaveable`.
- It is never part of the adapter, semantics, content description, screenshot fixture, test name,
  Logcat, evidence, saved-instance state, or process recreation state.
- It clears on terminal result, dismissal/root change, rotation, background policy transition, and
  failed persistence.
- IME and TalkBack expose the field label/state but not its value.
- Evidence uses generated non-secret fixture keys and records only fixed labels and lengths if
  needed.

### 6.3 Accessibility and layout

- one heading and one status live region; operation start/terminal is announced once;
- errors move focus to their heading only once per new terminal generation;
- after a recovery attempt completes, focus returns to the current error heading or the next root's
  existing first control;
- passphrase, confirm, cancel, and recovery targets are at least 48dp;
- actions stay adjacent to the affected state;
- 200% font, English 30% expansion, small/long screen, landscape, tablet/foldable, IME, safe area,
  gesture inset, and reduced motion must not hide the current fact or action;
- dark mode changes only semantic surfaces/contrast/elevation, not hierarchy or meaning.

User or remote-host switching is not reachable before successful local database initialization.
The plan records it as `NOT REACHABLE` for this root batch rather than adding identity logic.

While `unauthorized == true`, auth remains the only focus/IME/action owner. P01 semantics must not
exist in the merged tree, and TalkBack traversal must not reach database content.

## 14. Stop conditions

Stop and record a blocker only for:

- a required fix needs `Core.kt`, Haskell/native, protocol, database/schema/archive semantics, or
  iOS changes;
- safe proof requires a real user's database, personal key, production signer, destructive external
  action, or unavailable private account;
- no disposable fixture can distinguish a release-blocking state after safe alternatives are
  exhausted;
- the same unavoidable condition repeats for three Goal turns with no material progress.

Ordinary build, emulator, network, snapshot, or fixture failures are diagnostics to investigate.
Independent tests/docs/evidence continue while a non-global blocker is isolated.
