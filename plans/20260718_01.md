## 1. Problem statement

Nome Android 已经具备以下冻结成果：

1. 官方 `v6.5.6` 基线、API 28 最低版本、Android-only 设计基础和 Dark Token v1；
2. Phase 2 Batch 2 的 production shell 与 P07/P08 有界首页；
3. 本地检查点 `fa95d96c...`；
4. Phase 2 Batch 3 的 P13 源码、测试和大部分真实设备证据。

但 P13 尚未冻结，P01–P06、P09–P12、P14–P24 以及 Android 可达 P1 页面族还没有形成完整
Nome 产品。P01–P24 只是 P0 效果页集合，不是全部可达产品边界；产品合同还要求聊天工具、
联系人详情、群组/频道管理、媒体、通话、通知、身份与隐私、数据库恢复、高级网络、外观、
远程桌面、帮助以及 Android 系统入口全部 Nome 一致
（`apps/multiplatform/product/views/nome-android.md:19-28,46-61`；
`plans/20260716_03.md:396-416`）。

当前 P13 仍缺少精确命令计数、成功 in-flight 生命周期、部分异常、TalkBack 焦点/播报和
同摘要两轮复核
（`plans/evidence/20260717_nome_android_phase2_batch3_p13/remaining-gates.md:3-20`）。
因此新线程不能把现有 P13 当成已完成，也不能直接跳到 P14。

## 2. Solution summary

采用“**一个长期 Goal + 多个小型可冻结 batch + 最终全量 release-candidate gate**”的执行方式：

1. 新线程创建一个长期 Goal，持续到本地 release-candidate 真正完成；
2. 先闭合并本地 checkpoint P13；
3. 按依赖顺序实现 P01–P24，并把每个 P0 家族对应的 P1 可达页面一同收口；
4. 每个 batch 只拥有一个页面、一个紧密耦合页面对，或一个跨页面真值契约；
5. 每个 batch 都执行 product/spec/source 同步、自动化、API 28/API 35、真实 core、无障碍、
   截图、威胁模型、release 隔离、摘要和两轮 `ZERO ISSUES`；
6. batch 完成后允许创建本地 checkpoint commit，但绝不 push；
7. 所有 batch 完成后再执行一次跨页面、跨入口、升级、性能、安全和发布包总门禁；
8. 完成 AGPL、资产、品牌、application identity、App Links、隐私和分发材料的本地发布准备
   审计，但不执行外部发布；
9. 只有最终完成定义全部满足，才允许把 Goal 标记为 `complete`。

该方案避免一个超大不可审查 diff，同时允许 Goal 跨上下文压缩和新会话恢复。任何 renderer、
fixture、预览图或客户端推断都不能替代 production route、平台回调、API/core 返回和对端观察。

## 4. Detailed technical design

### 4.1 长期 Goal 状态模型

新线程创建 Goal 后，在
`plans/evidence/20260718_nome_android_completion/README.md`
维护唯一的总执行账本。每次可恢复检查点必须记录：

| 字段 | 要求 |
|---|---|
| 当前 milestone / batch | 唯一 in-progress 项 |
| 基线 | HEAD、branch、tag ancestry、dirty/staged 数 |
| 授权边界 | 本地 commit 是否已授权；remote push 始终否 |
| 最近完成 | batch plan、evidence root、commit、测试结果 |
| 当前 blocker | 事实、复现命令、影响范围、已试替代路径 |
| 下一动作 | 一条可直接执行、不会重新规划的动作 |
| 排除文件 | 已知用户/重复/外部文件列表 |

每次上下文压缩、设备重启或新会话恢复时，先读总计划、总账本和当前 batch 的
`remaining-gates.md`，然后从唯一下一动作继续。不得因为 Goal 持续时间长而重做已冻结 batch。

### 4.2 Batch 大小和依赖规则

一个 batch 最多包含：

- 一个独立 P0 页面；
- 一个共享同一 controller/state machine 的紧密页面对；或
- 一个被两个以上页面共同依赖、无法安全分开的 typed truth/permission/lifecycle 契约。

不得以“顺便统一”为理由做全局重构。跨页面 primitive 只有在第二个真实消费者出现且明显减少
总风险时才抽取。每个 page presenter 只投影现有 model/API/platform truth，不创建第二个 store、
navigation root、controller 或 native 调用路径。

### 4.3 能力分类

每个状态在 batch plan 中先分类：

| 类别 | 含义 | 可发布处理 |
|---|---|---|
| A | core/API/event 直接提供 | 可显示，必须有真实 core/API 证据 |
| B | 客户端可从稳定真值安全派生 | 可显示，必须有纯函数/状态测试和 production route |
| C | 当前产品没有可靠真值或恢复合同 | 删除、降级或明确不支持；不得 renderer-only 冒充完成 |

任何新发现的 C 项必须更新 `product/gaps.md`。若现有已冻结产品决策已经指定删除或降级，
Goal 可按该决策继续；若会改变信息架构、数据语义或安全承诺，则记录阻塞并先推进其他独立 batch。

### 4.4 最小可观测性合同

为闭合 P13 及后续 single-submit/lifecycle 门禁，Goal 明确允许添加一个**最小、无秘密、
测试/调试可观测**的计数接口，但必须满足：

- 不记录命令 payload、URI、二维码、owner signature、身份内容或服务器凭据；
- release 构建中无 debug activity、fixture、计数面板、测试 receiver 或可导出入口；
- 只暴露事件种类、attempt ID、生命周期阶段和 success/failure/cancel 分类；
- production 行为不依赖 observer 是否存在；
- 无 observer 时零额外网络/持久化行为；
- 静态扫描、release APK/dex/resource/manifest 扫描和运行时 Logcat/UI-tree 扫描证明隔离。

如纯 test seam 足以证明，不得扩大为生产日志系统。

### 4.5 每个 batch 的固定流水线

#### Gate A — 只读恢复

1. 读取总计划、总账本、当前 batch plan、相关 product/spec/source 和前一 batch final manifest。
2. 实测 Git、Gradle/JDK/SDK/ADB、API 28/API 35 AVD、磁盘和历史 manifest。
3. 记录 protected/forbidden paths；不修改历史 evidence。

#### Gate B — 设计和威胁模型

1. 画出 route → model/API/platform → reducer → UI → cleanup 的完整数据流。
2. 列举全部 sealed variants、错误、取消、重复点击、旋转、后台、process recreation、
   user/remote-host switch 和 stale callback。
3. 明确 A/B/C 分类、fallback 和不支持文案。
4. 先更新 batch plan；连续两次计划自审 `ZERO ISSUES` 后才写源码。

#### Gate C — 实现

1. 优先写 reducer/adapter/controller contract 测试。
2. 只添加最小 source seam 和 Android renderer；保留 legacy/Desktop fallback。
3. 同步更新 product/spec/source/test map。
4. 资源必须 zh-CN/en 成对；不引入新依赖，除非计划证明不可替代。

#### Gate D — 自动化

至少执行并归档适用命令：

- focused common/Android/desktop unit tests；
- `:android:compileDebugKotlin`；
- `:android:testDebugUnitTest`；
- `:android:lintDebug`；
- `:android:assembleDebug`；
- `:android:assembleDebugAndroidTest`；
- release manifest 与 release APK assembly；
- focused instrumentation、Compose semantics、screenshot tests；
- `desktopTest`；
- resource parity、expect/actual cardinality、source-anchor、forbidden-path、secret、release-isolation、
  duplicate-file、`git diff --check` 和 staged/remote audit。

先从当前 Gradle project 发现准确 task，不能把不存在的任务写成 PASS。

#### Gate E — 真实设备和真实行为

- API 28 clean install/cold launch/real core；
- API 33 权限、通知、后台服务、媒体/文件和 system back smoke；
- API 35 当前包升级、非空数据库、cold/warm intent 和 lifecycle；
- 有跨端语义的页面使用两个受控客户端；
- 权限、通知、camera、SAF、PiP、predictive back 等用真实 Android 平台入口；
- success 只由 API/core/platform terminal result 或对端观察证明；
- debug renderer 只证明视觉分支，不证明 production reachability。

#### Gate F — 视觉和无障碍

每个适用稳定状态至少覆盖：

- zh-CN/en；
- light/dark；
- 100%/200% 字体；
- API 28/API 35 中与兼容性相关的状态；
- 48dp、safe area、IME、gesture inset、无裁切/遮挡；
- English 30% 文案膨胀、减少动态效果、小屏/长屏/横屏；
- TalkBack role/name/state/traversal、error/live announcement、dismiss 后焦点恢复；
- 与已批准 P0 页面或明确相邻 P0 component family 的 side-by-side/overlay。

矩阵可以用 deterministic renderer 生成，但必须另有 production route 证据。

#### Gate G — 冻结和本地 checkpoint

1. 完成 README、truth table、build、device、screenshots、accessibility、threat-model、
   release-isolation 和 remaining-gates。
2. `remaining-gates.md` 必须为空或只含明确非发布范围；任何 release blocker 都不得藏在说明中。
3. 冻结一个 `REVIEW_INPUT_SHA256SUMS`。
4. 两个独立 reviewer 对同一摘要连续报告 `ZERO ISSUES`；任何修复使摘要失效并从 Round 1 重来。
5. 生成 final `SHA256SUMS`，验证历史 manifests 未变化。
6. 运行 `git diff --check`、secret scan、staged audit。
7. 本 Goal 的启动指令明确授权后，创建一个包含该 batch source/docs/tests/evidence 的本地
   checkpoint commit；排除已知用户文件，不 push。
8. 更新总账本后再进入下一个 batch。

| 风险 | 缓解 |
|---|---|
| 全项目 Goal 形成超大 diff | 强制小 batch、每批冻结、每批本地 commit |
| 当前 dirty tree 被误清理 | 禁止 reset/clean/stash/覆盖 checkout；每批记录排除文件 |

## 8. Stop and blocked conditions

Goal 应自动推进所有安全、可逆、计划内动作，不因普通失败等待用户确认。可以先推进不依赖当前
blocker 的独立 batch。

仅以下情况允许停止对应分支：

- 必须修改永久禁止的 core/protocol/database/archive/iOS 边界；
- 需要真实个人账户、真实用户数据库、生产密钥或不可逆外部操作；
- 发现来源不明 dirty work 与计划修改同一行，无法安全合并；
- 历史冻结 manifest 不匹配且不能解释；
- 必须做新的、会改变产品信息架构或安全承诺的业务选择；
- 需要 push、创建 PR、应用商店发布、生产签名或外部消息。

使用 Goal 状态时，只有同一 blocker 连续三个 Goal turn 均无法取得实质进展，才可标记
`blocked`；必须记录复现、已试替代方案、未完成 criteria 和恢复所需的最小用户输入。
