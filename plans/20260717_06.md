## 5. Detailed technical design

### 5.1 Production route and ownership

The retained route is:

```text
Android ACTION_VIEW intent
  -> MainActivity.processIntent
  -> ChatModel.appOpenUrl
  -> unchanged onboarding-complete + chatRunning gate
  -> connectIfOpenedViaUri
  -> planAndConnect
  -> apiConnectPlan (real core)
  -> eligible identity-choice branch
  -> Android Nome P13 modal
  -> exactly one apiConnect attempt
  -> returned PendingContactConnection
  -> chatsContext.updateContactConnection
```

P13 does not become a new navigation owner and does not receive a direct route from the P07 home.
It is a privacy-sensitive modal over the current production root. `connectIfOpenedViaUri` is the
only caller that opts in with an explicit `ExternalActionView` presentation policy. The policy
parameter on `planAndConnect` defaults to `Legacy`, so `NewChatSheet.kt`, `NewChatView.kt`,
the `ChatListView.kt:connect(...)` SimpleX-link search call, `ChatPreviewView.kt`,
`FramedItemView.kt`, and `GroupMemberInfoView.kt` retain their current UI and cleanup behavior.
Android may present P13 only when both the external policy and an eligible plan branch are present;
Desktop always retains legacy behavior.

`rhId`, current user identity, and the original link session are captured at plan time. Before
every connect attempt, the presenter must verify that the same user/host is still active; a
mismatch cancels and replans instead of sending under a different identity.

Back, system dismiss, and explicit cancel call one idempotent cleanup closure. Cleanup clears the
ephemeral link/session, closes P13, restores focus, and resets
`ChatModel.appOpenUrlConnecting`; it never sends `CC.APIConnect`.

### 5.2 Eligible branches and mandatory fallback

The platform P13 seam is offered only where the current controller already calls
`askCurrentOrIncognitoProfileAlert`:

| Core plan branch | P13 treatment |
|---|---|
| `InvitationLinkPlan.Ok` without short-link preparation data | Fresh invitation preview |
| `InvitationLinkPlan.OwnLink` | Destructive own-link warning; no “verified contact” wording |
| `ContactAddressPlan.Ok` without short-link preparation data | Fresh address preview |
| `ContactAddressPlan.OwnLink` | Destructive own-address warning |
| `ContactAddressPlan.ConnectingConfirmReconnect` | Explicit repeat-request warning |
| `GroupLinkPlan.Ok` without short-link preparation data | Identity/source preview only; no P16 group-detail claims |
| `GroupLinkPlan.ConnectingConfirmReconnect` | Explicit repeat-join warning |

Every other variant retains the existing controller path in Batch 3:

- invitation/contact/group short-link preparation stays with `showPrepareContactAlert` /
  `showPrepareGroupAlert`;
- `Known`, `ContactViaAddress`, `ConnectingProhibit`, and known group paths continue opening or
  describing the authoritative existing object;
- `GroupLinkPlan.OwnLink`, `NoRelays`, and `UpdateRequired` keep their current group-specific path;
- `ConnectionPlan.Error` keeps the current upstream fallback and is never labelled plan-ready;
- P12 scanning/pasting, P14 request mutation, and P16 group detail/join are not implemented.

This exhaustive routing preserves every currently handled `ConnectionPlan` subtype
(`apps/multiplatform/common/src/commonMain/kotlin/chat/simplex/common/model/SimpleXAPI.kt:7088-7128`)
and prevents an unsupported branch from falling into a blank Nome page.

### 5.4 Safe UI model

The Android route receives only display-safe facts:

- link kind: invitation, address, or group;
- action consequence and destructive/repeat flag;
- current user display name/avatar already visible to that local user;
- identity selection: current profile or new incognito profile;
- owner verification display state: absent, `Verified`, or `Failed(reason)`;
- operation state: ready, connecting, pending, failure;
- sanitized source label derived from the typed target, never the full URI.

`CreatedConnLink`, the original URI, `LinkOwnerSig`, and retry token remain only in an ephemeral
common controller closure. They are not saveable state, `ChatModel` fields, analytics, logs,
semantics text, screenshot fixtures, evidence filenames, or product/spec examples. Cleanup drops
the closure. A configuration change may restart plan resolution but must not serialize a bearer
link into UI state.

Owner verification copy maps only the core’s `OwnerVerification.Verified` or
`OwnerVerification.Failed(reason)` result
(`apps/multiplatform/common/src/commonMain/kotlin/chat/simplex/common/model/SimpleXAPI.kt:7088-7090`;
`apps/multiplatform/common/src/commonMain/kotlin/chat/simplex/common/views/newchat/PlatformConnectionPreview.kt:251-256`).
It must not say that the contact, group admin, channel operator, server, or connection is verified.

### 5.5 State machine and command boundary

```text
PLAN_READY(current selected)
  <-> PLAN_READY(incognito selected)
  -> CONNECTING
       -> PENDING(real returned connection)
       -> FAILURE(typed outcome retained)
            -> REPLANNING
                 -> PLAN_READY / authoritative fallback
  -> CANCELLED
```

Rules:

1. `PLAN_READY` exists only after one successful typed `apiConnectPlan` response. The client does
   not infer validity from link shape. A typed sibling/delegate preserves plan failure and
   cancellation for P13 while the legacy `apiConnectPlan()` wrapper preserves existing alerts for
   all non-P13 callers.
2. Current/incognito are mutually exclusive. Incognito means a new random profile for this
   connection, not a persistent anonymous account
   (`apps/multiplatform/product/flows/connection.md:180-192`).
3. Continue is single-submit. While `CONNECTING`, all connect actions are disabled and
   accessibility state explains why.
4. The P13 path calls typed siblings/delegates around the existing `CC.APIConnectPlan` and
   `CC.APIConnect`; it adds no command, response, event, protocol, or database change. The legacy
   `apiConnectPlan()` and `apiConnect()` wrappers keep existing behavior for non-P13 callers
   (`apps/multiplatform/common/src/commonMain/kotlin/chat/simplex/common/model/SimpleXAPI.kt:1563-1570,1602-1617`).
5. Only `CR.SentConfirmation` or `CR.SentInvitation` returns a pending connection and permits the
   transition to `PENDING`. `CR.ContactAlreadyExists`, `API.Error`, network failure, cancellation,
   and an identity/host mismatch are distinct non-success outcomes.
6. P13 updates `chatsContext` only with the real returned `PendingContactConnection`, preserving
   the existing update point
   (`apps/multiplatform/common/src/commonMain/kotlin/chat/simplex/common/views/newchat/ConnectPlan.kt:446-465,545-555`).
7. Retry repeats plan resolution and then connect. If the authoritative plan changes to a
   non-P13 branch, P13 closes and delegates to that existing branch; it must not connect using a
   stale plan.
8. Cancellation propagates as cancellation, clears in-flight state exactly once, and is never
   rendered as a network error.

### 5.6 UI and accessibility contract

The page contains:

- title and safe source/type summary;
- current-profile and new-incognito identity cards;
- exact per-connection consequence copy;
- owner/source warning when present;
- cancel/back and one primary continue/retry action;
- indeterminate connecting state;
- response-driven pending state; and
- typed failure with retained identity selection and retry.

Required behavior:

- zh-CN and English resource-name parity;
- light and dark using existing Nome semantic tokens;
- 100% and 200% font without clipping, overlap, or hidden actions;
- every interactive target at least 48dp;
- TalkBack order: title, source/type, warning, current identity, incognito identity, selected state,
  primary action, cancel;
- role/state/selection semantics and live announcements for connecting, failure, and pending;
- no color-only warning or selection;
- focus moves to the failure heading on error and to pending heading on success;
- raw links, real personal identities, and real owner signatures never enter screenshot fixtures.

### 5.8 Threat-model delta

| Threat | Required control | Required proof |
|---|---|---|
| Wrong local user or remote host receives the command | Bind user/`rhId` at plan time; recheck before connect/retry; cancel on mismatch | unit race tests plus real profile/host-switch trace |
| Bearer connection link leaks through logs, state, semantics, or evidence | Keep raw link in ephemeral common closure; sanitize display; scan artifacts for URI/token patterns | static scan, Logcat scan, UI-tree scan, evidence scan |
| Owner verification is overstated | Map only `Verified`/`Failed`; prohibit contact/admin/server verification wording | exhaustive mapping tests and bilingual copy review |

   foreground, and retry do not duplicate it.

   `PendingContactConnection`; no fixture, timeout, toast, or client inference can create success.
6. Plan failure, connect failure, already-existing contact, cancellation, and identity/host
   mismatch are not collapsed into success or one generic null.
7. Retry reruns planning, retains the user’s identity selection when safe, and delegates changed
   plans to the authoritative existing branch.
8. Cancel/back/dismiss sends no connect command, invokes cleanup exactly once, clears the ephemeral
   bearer link, resets `appOpenUrlConnecting`, and restores focus.
9. Owner verification copy maps only the returned core fact and never claims verified contact,
   admin, channel, server, or transport.
10. Every non-P13 `ConnectionPlan` variant retains a working existing fallback; P12 and P16 do not
    acquire partial Nome implementations.
11. Android UI is bilingual, light/dark, 100%/200%, 48dp, TalkBack traversable, and free of
    clipping/overlap/color-only meaning.
12. Debug fixtures are excluded from release and never substitute for API 28/API 35 real-core and
    two-client evidence.
13. No raw bearer link, real personal identity, or owner signature enters logs, semantics,
    screenshots, filenames, manifests, or prose.
14. `CODE.md`, product concepts, spec index, product/spec/source/test/evidence links, and every new
    file in their document maps are coherent; two same-digest reviews report consecutive
    `ZERO ISSUES`.
15. Haskell/native core, `Core.kt`, protocol, command/event contracts, database/archive format,
    message state machine, iOS, Desktop UI, P09–P12, and P14–P24 remain unchanged except for
    truthful cross-layer documentation needed to describe P13.
