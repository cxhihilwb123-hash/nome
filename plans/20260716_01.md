## 1. Problem Statement

Nome 已完成 Android 与 iOS 的 24 页核心视觉设计，但当前 `simplex-chat` 原生仓库仍是未经 Nome 改造的官方 SimpleX Chat 6.5.6。下一阶段需要先开发 Android 版本：保留官方通信核心、安全模型、本地数据和系统能力，用 Nome 品牌、中文优先的产品语言和更高级、简约、易操作的 Android 外壳重构用户体验，并确保设计稿中的页面与状态落到真实业务行为，而不是只做静态页面。

当前还存在三个必须先解决的工程条件：

1. Git 位于浅克隆的 detached HEAD，尚无 Nome 开发分支；唯一 `origin` 是官方仓库，必须视为只读。
2. 当前 shell 未配置 Java；仓库缺少 `local.properties` 以及与 v6.5.6 对应的 `libsimplex.so`、`libsupport.so`，尚未证明未改动 APK 可构建。
3. 主要 Compose UI 位于 KMP `commonMain`，同时服务 Android 与 Desktop；Android 改版不能意外改坏 Desktop，也不能绕过现有 `ChatModel → ChatController → JNI → Haskell core` 链路。

## 2. 目标、范围与非目标

### 2.1 本轮目标

- 先交付可安装、可真实使用、默认简体中文且完整支持 English 的 Nome Android 版本。
- 原生实现 P01–P24 全部核心页面，并覆盖设计规范列出的必需状态。
- 盘点并统一 Nome 化 P01–P24 之外所有仍可达的官方 6.5.6 功能表面，避免主流程换壳后从二级页面掉回半套 SimpleX 旧界面。
- 保留官方 SimpleX 6.5.6 的核心能力、安全语义、数据兼容和 Android 系统集成。
- 建立可复用的 Nome Design System，使后续 iOS 版本可以沿用同一产品语言与视觉规范。
- 以真实构建、设备运行、双端业务验证和原生截图对照作为完成证据。

### 2.2 本轮范围

- `apps/multiplatform/android` 的 Android 壳、Manifest 相关显示资源和系统集成。
- `apps/multiplatform/common` 中 Android 所需的 Compose UI、资源、状态映射及必要的共享组件。
- 新安装默认简体中文、English 切换、所有新增可见文案的资源化。
- 设计规范 P01–P24、明暗模式、状态页、权限反馈、无障碍和响应式适配。
- Android API 26、33、35 的验证，以及小屏设备的首发适配。
- 与改动对应的 `product/`、`spec/`、测试和开发证据同步。

### 2.3 明确不在本轮范围

- 不开发 iOS；iOS 仅保留已有设计资料。
- 不重做已经批准的视觉方向，不回退到被淘汰的 `../design/design/product/pages/`。
- 不重写 Haskell core、JNI、协议、数据库格式、消息状态机或连接算法。
- 不迁入其他旧 checkout 的 custom core、Nix patch、历史 Nome 批量提交或旧 iOS 证据。
- 不把 React 原型代码、演示头像或场景素材直接打包进生产 App。
- 不在 UI 开发早期更改正式 applicationId、签名、域名和 App Links；这些属于发布决策门。
- 不向任何远端推送；开发线程只做本地、可审查的阶段性提交，除非用户在当时明确授权推送。

## 4. Solution Summary

采用“Android 专用 Nome 外壳 + 官方共享状态/API + 渐进式共享组件”的混合方案：

```text
Android Activity / 系统能力
        ↓
Nome Android Shell / Navigation / Platform adaptation
        ↓
Nome tokens + reusable Compose components
        ↓
Existing official screen state and leaf functionality
        ↓
ChatModel → ChatController → JNI Core → Haskell core
```

核心决策：

- 冻结 core 边界，优先复用真实状态和 API，不复制业务逻辑。
- Android 平台结构明显不同的部分放在 `androidMain`、Android 模块或 `expect/actual`；共享基础组件才进入 `commonMain`。
- 第一版继续使用现有 Compose Material 2 API，并实现接近 Material 3 的尺寸、层级、edge-to-edge、Bottom Sheet、导航和触控行为；不把 24 页改版与整库 Material 3 迁移绑定。
- 所有页面按状态驱动，不创建仅供截图使用的假数据分支。Preview/fixture 可用于开发，但生产路径必须来自现有 model/controller。
- 每批页面同时完成正常、加载、空、离线、错误、权限拒绝和危险确认等适用状态；不把异常状态全部拖到最后。

## 5. Detailed Technical Design

### 5.1 应用启动与安全状态门

官方启动链保持不变：

1. `SimplexApp.onCreate()` 加载 native core、迁移、数据库和控制器。
2. `MainActivity.onCreate()` 处理语言、通知、深链、分享、隐私和 edge-to-edge。
3. `AppScreen()` / `MainScreen()` 决定迁移、数据库、启动、欢迎、锁屏、聊天、通话和全屏弹层。

`App.kt` 中迁移、数据库错误、初始化、欢迎流程和应用锁的先后次序具有恢复与安全意义。Nome 只能替换对应分支的表现与组件，不允许为了导航简化而重排状态门。

### 5.2 Nome Design System

建立集中式 tokens 和组件层，不在页面散落颜色、圆角和尺寸：

- 颜色：品牌主色、中性色、背景层、容器层、边框、信息/成功/警告/危险、安全状态、暗色映射。
- 字体：中文优先字阶、English stress 字阶、数字/代码/安全码样式、系统字体 fallback。
- 形状与尺寸：4/8dp 网格、按钮/输入/卡片/Sheet 圆角、48dp 最小触控区、系统栏和导航栏 inset。
- 基础组件：Top App Bar、Bottom Navigation、FAB、按钮、图标按钮、输入、搜索、列表行、会话行、卡片、Section、Badge、Avatar、Toast/Banner、Dialog、Bottom Sheet、Skeleton、Empty/Error/Offline State。
- 业务组件：连接入口卡、安全披露卡、身份选择器、relay 状态、消息气泡、发送状态、频道非 E2EE 提示、迁移进度。

实现策略：先建立 Android 可控的 Nome 组件，再按页面替换；只有确定 Desktop 也应共享的 token/组件才进入跨平台默认路径。每次触碰 `commonMain` 都必须运行 Desktop 回归并检查视觉没有被意外改版。

### 5.3 导航与页面状态

- 使用现有根状态和 Modal 导航为业务真相，新增 Nome 页面枚举/路由仅作为展示编排层。
- 首页保持设计稿的紧凑会话密度、三类连接入口和清晰未读层级。
- 流程型页面（连接、频道、迁移）使用可恢复的显式状态模型；进程重建后不落到错误步骤。
- Android 系统返回、手势返回和后续 predictive back 必须有一致的关闭/回退语义。
- Modal、Bottom Sheet 和全屏流程不得吞掉正在进行的 core 操作或重复发起命令。

### 5.4 语言与文案

- 不能用 `appLanguage == null` 单独判断“新安装”，因为上游已有用户也可能明确处于跟随系统模式。
- 增加一个版本化、一次性的 Nome locale 初始化标记，并在 spec 中定义判定表：
  1. 标记已存在：不再初始化。
  2. `appLanguage` 已有显式值：原值不变，只写入标记。
  3. `appLanguage == null` 且存在既有数据库/用户/偏好或明确的升级证据：继续保持 system，不改用户行为，只写入标记。
  4. `appLanguage == null` 且由安装元数据与“无既有 App 数据/用户”共同证明为全新安装：设置 `zh-CN`，再写入标记。
  5. 无法可靠判断时按既有安装处理，宁可保留 system，也不覆盖用户偏好。
- 对清数据新装、v6.5.6 升级且 language=null、显式 English、显式中文、备份恢复/系统 restore 分别建立测试；升级判断不得把个人信息写入日志。
- 同时测试显式其他上游语言和损坏/未知语言代码；任何非法值都必须安全回退，不能启动崩溃或静默覆盖数据。
- 设置页可切换简体中文与 English；首发质量承诺覆盖这两种语言。
- 所有新增可见文案使用 MR 资源，禁止在 Composable 中硬编码中文或英文。
- English 使用约 30% 文案膨胀做布局压力测试；中文检查断行、标点和术语统一。
- 其他上游语言资源开发期可保留并回退，但不能误报为 Nome 首发已完整验证。
- “SimpleX” 作为底层协议/兼容性/法律说明时不盲目替换；面向用户的产品品牌、图标、通知和启动页统一为 Nome。

### 5.5 Android 系统边界

视觉改造必须保留并回归：

- `ACTION_VIEW`、`simplex:` 深链和官方兼容链接。
- `ACTION_SEND` / `ACTION_SEND_MULTIPLE`、FileProvider、文件选择器。
- 相机扫码及权限拒绝/永久拒绝反馈。
- Android 13+ 通知权限、通知渠道、后台接收与前台服务。
- 开机恢复、电池优化提示、通话 Activity/Service、全屏通知和 PiP。
- `FLAG_SECURE`、应用锁、BiometricPrompt/device credential。
- edge-to-edge、状态栏/导航栏、刘海安全区、IME 和键盘遮挡。

开发期保留 `chat.simplex.app` 和 debug applicationId suffix，继续支持 `simplex:` scheme。正式包名与 Nome 域名迁移必须在发布门中单独决定并验证升级/共存策略。

### 5.6 核心与数据边界

以下默认冻结：

- Haskell `src/` 与 native core。
- `Core.kt` JNI 声明。
- 数据库 schema、归档格式和迁移协议。
- 消息状态机、连接协议、relay 语义和加密语义。

若页面需求确实缺少官方 API，先记录能力差距、product/spec 影响和最小替代方案；必须经过单独计划与用户决策，不能夹在视觉提交中修改 core。

### 5.7 安全与隐私语义

- 不显示 core 无法证明的在线状态、已读状态、加密状态或 relay 健康。
- 一次性邀请与可复用公开地址必须使用不同术语、图标和失效说明。
- 群组加入前显示来源、公开/私密、审批要求和风险提示。
- 公开频道必须持续显示“不是端到端加密”的准确披露，不能套用私聊安全文案。
- 身份是本地身份，不使用“云账号、登录、云同步”心智模型。
- 备份/迁移必须清楚说明本地文件、取消、失败恢复和危险操作。
- 删除身份、替换公开地址、清理数据、停止迁移等破坏性动作使用二次确认。

## 7. Detailed Implementation Steps

### Phase 0 — 冻结基线与创建开发分支

任务：

1. 记录 `git status`、tag、完整 commit、shallow 状态、remotes 和设计路径。
2. 从当前提交创建本地分支 `codex/nome-android-v656`。
3. 把官方 `origin` 视为只读；不 pull、不 push、不改 remote。
4. 记录权威设计文件清单和哈希，确认 24 张 Android PNG 齐全。
5. 从现有导航、Modal、设置入口、深链和系统 Intent 建立“全部可达功能表面”清单；P01–P24 是有逐页效果图的核心子集，不是全部 Composable 的边界。
6. 新建 `plans/20260716_03.md`（标题：`Nome Android 页面与状态覆盖矩阵`），字段至少含：页面/入口、P0 或 P1、状态、语言、主题、源入口、product/spec、测试、截图、无障碍、真实业务证据、完成状态。
7. 对没有独立效果图的 P1/二级页面在矩阵中指定复用的 Nome 组件/参考页；若信息结构超出已有规范，先补产品/状态设计说明再改代码。

`NOME_ASSETS_DIR` 是按仓库 overlay/verification 规则整理后的获批 Nome 资源目录，不等于直接把 React 原型或任意 brand 文件夹传给构建。未配置正式签名时只能称 `unsigned internal RC`；完成正式签名后还要验证 APK/AAB 签名证书、可安装性、ABI、版本号和 SHA-256，才能称 signed RC。

注意：`generateMRcommonMain` 依赖 `adjustFormatting`，可能机械调整翻译 XML。每次 Gradle 执行后都要检查 `git status`，不要把无关翻译重排混入功能提交。

## 10. 风险、威胁模型与缓解

| 风险 | 影响 | 缓解 |
| --- | --- | --- |
| native 库版本不匹配 | 启动崩溃、隐蔽 ABI/core 问题 | 只用 v6.5.6 对应产物，记录来源和 SHA；先过未改动基线。 |
| detached/shallow/官方 origin | 丢提交或误推官方仓库 | 首步创建本地分支；origin 只读；当前任务不 push。 |
| 大范围改 `commonMain` | Desktop 意外改版或回归 | Android 专用 shell；共享改动最小化；每批跑 Desktop 回归。 |
| 同时迁 Material 3 | diff 过大、难以隔离回归 | 首版保留 Material 2 API，先用 tokens/组件实现 M3 体验。 |
| 视觉覆盖真实状态 | 假在线/假加密/错误失败语义 | UI 只消费官方 state/API；安全文案逐项与 core 对照。 |
| 默认中文覆盖老用户 | 升级后偏好丢失 | 仅新安装无值时初始化 zh-CN；已有有效值不改。 |
| 公开频道安全误导 | 隐私与合规风险 | 固定 non-E2EE 披露，所有频道入口和会话均验证。 |
| 迁移/删除误操作 | 用户数据丢失 | 保留官方协议，二次确认，可取消/恢复，使用测试数据验证。 |
| 仅做 happy path | 上线后权限/离线场景不可用 | 每批同时交付适用异常状态，不留到最终阶段。 |
| 资产许可冲突 | 修改版无法合法分发 | 发布前全量替换 SimpleX 专有图形资产并完成清单审计。 |
| 包名/域名过早改动 | 深链、升级、通知、签名混乱 | 开发期不改；独立发布决策与迁移测试。 |
| 截图驱动假实现 | 看起来完成但业务不可用 | 截图只是一个 gate；同时要求双端真实流程和 core 状态证据。 |

### 10.1 显式威胁模型

保护资产：本地身份与数据库、消息和附件、连接/安全码、备份归档、通知内容、语言/安全设置、签名与 native core 完整性，以及用户对 E2EE/频道/relay 状态的正确理解。

| 威胁主体与前置条件 | 可能攻击 | 控制措施 | 必须留下的验证证据 |
| --- | --- | --- | --- |
| 恶意联系人或链接发送者，可提供 crafted `simplex:` link/二维码/剪贴板文本 | 崩溃、重复连接、旧版本降级、诱导使用错误身份 | 复用官方 parser/version checks；预览来源/身份；非法、重复、过期、旧版显式失败；不在 UI 自行解析协议 | fuzz/边界样本、P12/P13 instrumentation、无崩溃 Logcat |
| 恶意群主、频道 owner、成员或不可信 relay | 欺骗公开/审批/角色/relay 状态，诱导用户把频道当 E2EE，垃圾/举报滥用 | 状态只来自 core；展示来源/角色/审批；频道入口与会话固定 non-E2EE 披露；保留举报/退出/失败恢复 | 双角色/恶意状态测试、P16/P20/P21 截图和 core event 记录 |
| 恶意外部 App 发送深链、share Intent、content URI 或超大/异常文件 | URI 权限滥用、资源耗尽、错误文件发送、路径或 MIME 欺骗 | 保留 FileProvider/temporary grants；校验 scheme/MIME/size/可读性；取消与错误反馈；不信任显示文件名 | ACTION_VIEW/SEND/SEND_MULTIPLE 测试、拒绝/超大/失效 URI 记录 |
| 恶意或损坏的备份/迁移归档 | 导入失败、资源耗尽、覆盖/数据丢失、路径穿越 | 保留官方 archive API/格式；在专用测试数据上验证；导入前确认与备份；失败回滚/恢复；不自行解压到任意路径 | 损坏/截断/错误密码/取消/重试/空间不足测试和数据库前后校验 |
| 获得设备、锁屏或通知访问权的本地攻击者/旁观者 | 窥视身份、消息、二维码、安全码、通知内容 | `FLAG_SECURE`、应用锁、Biometric/device credential、通知隐私选项、剪贴板/二维码敏感信息最小暴露 | 锁屏通知、recent screen、截图、失败解锁、重启后锁定测试 |
| 被替换、版本错配或来源不明的 native artifact | 在 core 层执行恶意代码、崩溃或产生不兼容数据 | 仅 exact v6.5.6 immutable artifact；archive/ELF SHA、ABI、build-id、来源记录；四库同批次；禁止 latest | provenance 文件、哈希、ELF 检查、未改动基线启动证据 |
| UI 实现者或状态映射错误（非恶意也可触发） | 展示虚假在线、已读、E2EE、relay 成功或迁移完成，误导用户执行敏感动作 | 页面状态映射表绑定 model/API/core event；缺能力写 `[GAP]`；安全词汇 review；禁止 mock 进入生产路径 | 每批 threat-model delta、状态追踪测试、截图+事件对照 |
| 升级/Locale 迁移逻辑在既有安装上运行 | 覆盖语言、安全设置或破坏数据 | versioned marker；可靠 fresh/upgrade 判定；同 suffix debug 原地升级；不确定时保持旧值 | fresh/upgrade/system/zh/en/legacy-invalid locale 与非空 DB 升级矩阵 |

每个开发批次都必须写“本批 threat-model delta”：新增入口、攻击者可控输入、受保护资产、控制、残余风险和验证。若没有新增安全面，也要明确写“无变化”及依据。

### 10.2 测试数据隔离

- 只使用专用 AVD/真机测试 profile、合成身份、测试消息和可丢弃附件；禁止使用用户个人身份、数据库、备份、联系人或正式 keystore。
- 日常包强制非空 `.nome.dev` suffix 和 `Nome Dev` 名称；每个 API/场景保留可恢复快照，破坏性迁移前再做设备快照和归档哈希。
- 双端测试使用两个隔离客户端/AVD，明确记录 relay/operator 与是否接触公网；日志和截图不得包含真实个人信息、token 或密钥。
- 数据删除、身份删除、损坏归档和空间不足只在可销毁环境执行；正式签名材料不进入普通开发线程。
