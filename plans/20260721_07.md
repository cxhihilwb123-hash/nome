# Nome iOS Dynamic Type and accessibility preview validation plan

Date: 2026-07-21
Status: complete

## 1. Problem statement

Nome iOS has current light/dark 14-state preview evidence, but the same product
surface has not been verified at accessibility Dynamic Type sizes. Several
Nome-facing views intentionally use one-line labels and scale factors, so a
normal-size screenshot pass cannot rule out clipping, overlap, hidden primary
actions, or icon-only controls without accessible names.

Android testing may be active on the same Mac. The initial audit therefore
reuses the already installed simulator app. If that audit confirms a source
defect, one controlled incremental iOS build/install is allowed only after a
live process check shows no running Gradle build/test task. Core preparation,
dependency installation and physical-device operation remain forbidden.

## 2. Solution summary

Use the booted iPhone 17 Pro simulator and the installed Nome build 337 to
establish before-fix evidence, then, only for confirmed source defects, perform
an incremental simulator build/install to:

1. capture the existing 14 deterministic preview states in light and dark at
   the system `accessibility-large` content-size category;
2. capture a smaller critical-route stress set at
   `accessibility-extra-extra-extra-large`;
3. review contact sheets and individual failures for clipping, overlap,
   unreachable primary actions, and unreadable contrast;
4. statically audit Nome-specific icon buttons, line limits, scale factors and
   accessibility labels where screenshots cannot prove VoiceOver semantics;
5. restore the simulator's original appearance, content size and increased-
   contrast setting even if capture fails.

The evidence remains preview-only and does not imply real-core communication,
physical-device VoiceOver, signing or App Store readiness.

## 3. Detailed technical design

### 3.1 Product and source scope

This batch covers PC32 Nome Product Experience and its existing overlay paths:

- `Shared/Views/Onboarding/`;
- `Shared/Views/ChatList/ChatListView.swift`;
- `Shared/Views/NewChat/`;
- `Shared/Views/Chat/ChatView.swift`;
- `Shared/Views/UserSettings/`.

The behavior contract comes from
`apps/ios/product/views/nome-experience.md`; technical preview isolation comes
from `apps/ios/spec/client/nome-brand-overlay.md`. No Haskell/native core,
database, protocol, release identifier or message state changes are allowed.

### 3.2 Matrix

Primary matrix:

- content size: `accessibility-large`;
- appearances: light and dark;
- states: home, four onboarding states, existing chat list, conversation,
  conversation details, identity center, add friend, join group, public
  contact, settings and contacts.

Stress matrix:

- content size: `accessibility-extra-extra-extra-large`;
- appearance: light, plus dark for any failure candidate;
- critical states: home, onboarding welcome, chat list, conversation, add
  friend, public contact and settings.

System content-size category names are recorded directly. The evidence must not
rename them as an exact percentage because text-style scaling differs by style.

### 3.3 Capture and restoration

The capture helper launches the already installed `chat.simplex.app` with the
existing preview arguments and takes `simctl io screenshot` images. It records
dimensions, bytes, SHA-256 and launch arguments in a TSV manifest and creates a
contact sheet when ImageMagick is available.

Before any setting change, record:

- `simctl ui <device> appearance`;
- `simctl ui <device> content_size`;
- `simctl ui <device> increase_contrast`.

A shell trap restores all supported original values. A successful screenshot
matrix without a successful restore is a failed batch.

### 3.4 Accessibility evidence boundary

Screenshots can prove visible layout and contrast but cannot prove VoiceOver
focus order or activation. Static source checks can prove explicit labels exist
for selected icon-only controls but cannot replace a real assistive-technology
run. Physical-device VoiceOver remains a separate unchecked gate.

### 3.5 Threat model

- **Hidden security or privacy copy:** accessibility-size screenshots must not
  clip trust explanations or replace them with ellipses that change meaning.
- **Hidden primary actions:** a large title must not push the only continue,
  add, close or send action outside a non-scrollable viewport.
- **False accessibility claim:** preview screenshots and source labels are not
  promoted to physical-device VoiceOver proof.
- **Simulator state leakage:** original appearance/content-size/contrast values
  are restored through a trap and verified afterward.
- **Android test interference:** captures are serial; before any iOS build, a
  live process check must show no active Gradle build/test. The one permitted
  incremental simulator build uses existing dependencies and does not mutate
  the Android worktree.
- **Preview/core confusion:** launch arguments and preview-only status are
  preserved in every manifest and summary.

## 4. Detailed implementation steps

1. Record iOS and Android protection baselines and the installed Nome app info.
2. Add a focused capture helper that requires an already installed app, changes
   only simulator UI preferences, restores them via trap, and never builds or
   installs.
3. Capture the light/dark `accessibility-large` 14-state matrices.
4. Capture the seven-state maximum-size stress matrix.
5. Generate manifests/contact sheets and visually inspect every state; inspect
   individual screenshots for every suspected failure.
6. Run a static source audit of Nome-facing line limits, scale factors,
   icon-only buttons and accessibility labels.
7. Fix only confirmed PC32 accessibility defects, updating product/spec/impact
   documentation and source anchors; if no defect is confirmed, change no
   Swift source.
8. If source changes are required, confirm Android build/test processes are
   idle, then perform an incremental iOS simulator build/install and repeat the
   failing matrices into distinct after-fix evidence paths. If visual review
   disproves a layout correction, focused incremental corrections are allowed
   only after repeating the same process check; failed evidence is retained
   outside the accepted evidence paths rather than overwritten.
9. Run focused script tests, syntax checks, brand/design gates, diff hygiene,
   simulator-setting restoration verification and two consecutive adversarial
   reviews.

## 5. Testable acceptance criteria

- All 28 `accessibility-large` screenshots exist, have stable dimensions,
  exceed the minimum byte threshold and have unique state hashes where expected.
- All seven maximum-size stress screenshots are captured and reviewed.
- No visible text/control overlap, destructive truncation or non-scrollable
  hidden primary action remains in the accepted evidence.
- Suspected issues are confirmed from individual full-resolution screenshots,
  not contact-sheet thumbnails alone.
- Static audit results distinguish explicit labels, visible-text labels and
  unresolved VoiceOver-only checks.
- Original simulator appearance, content size and increased-contrast values are
  restored and recorded.
- Controlled incremental iOS build/install work occurs only after the Android
  activity check; no real-Core preparation, Android mutation or remote push
  occurs.
- Two consecutive final reviews report `ZERO_ISSUES`.

## 7. Execution result

In progress. The first light capture attempt stopped before its first
screenshot because Bash 3.2 with `set -u` rejected expansion of an empty launch
argument array for the home case. The restoration trap passed and restored the
original simulator settings. The helper now calls the no-argument case without
an empty-array expansion; the incomplete output is retained outside the final
evidence path for diagnosis.

The corrected light matrix captured 14/14 states. The dark matrix also captured
14/14 states and restored settings, but the local ImageMagick installation had
no usable font configuration and returned non-zero while composing the contact
sheet. Contact-sheet generation now prefers the installed `ffmpeg` tile filter
and degrades to a warning instead of invalidating already verified source
screenshots.

Full-resolution review confirmed three PC32 defects: onboarding pills lost
meaning through ellipses at `accessibility-large`, the conversation security
banner compressed and overlapped its own content, and the disappearing-message
prompt truncated at the maximum size. A live process check found only idle
Gradle/Kotlin daemons and no running Android build or test, so the plan now
permits one controlled incremental iOS simulator build/install to verify the
focused SwiftUI fixes.

The first after-fix matrices proved that onboarding pills and the disappearing-
message prompt were corrected, but they also disproved the initial assumption
about the security banner: its children grew while the containing chat
`VStack` still compressed the banner's allocated height. Text therefore
rendered outside the banner's layout slot and over the first messages. That
evidence is retained as a failed intermediate result. A second live Android
check again found only 0.0% idle Gradle/Kotlin daemons. The corrective patch
gives the banner and prompt their intrinsic vertical size and layout priority
before a second incremental build and conversation-only recheck.

That recheck proved the card's own intrinsic height but still showed messages
painting beyond the custom viewport. The final corrective step clips the
message `ZStack` to its allocated layout slot. A third live process check again
found no active Android build/test. The final incremental build passed, and
focused light/dark conversation captures passed at `accessibility-large` and
`accessibility-extra-extra-extra-large`; a normal `large` capture also passed.

Accepted evidence is composite: the 14-state light/dark matrices and seven-
state light/dark maximum-size matrices are under the `*-fixed-20260721`
directories, with their conversation rows superseded by the corresponding
`*-accepted-20260721` focused captures. Three key before-fix screenshots and
the live `serve-sim` frame are stored under
`plans/evidence/20260721_nome_ios_accessibility/`. Full failed intermediate
matrices remain archived at
`/private/tmp/nome-ios-accessibility-intermediate-20260721` rather than adding
them to the repository worktree.

The final full-Xcode incremental build exited 0. The live readiness aggregate
reported 46 PASS, 5 WARN, 8 known BLOCKED and 0 FAIL. The WARN/BLOCKED rows are
the existing real-core, physical-device, final-store-screenshot, manual-QA and
release-identity boundaries; this batch does not promote them to completion.
