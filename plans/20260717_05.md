### Stage 0 — 现场恢复与保护检查

### Stage 1 — Gradle 启动与 Kotlin 编译

从 `apps/multiplatform` 使用 Android Studio JBR：

1. `./gradlew --version`
2. `./gradlew :android:compileDebugKotlin`
3. 若失败，先区分环境/依赖、Gradle 配置、Kotlin 编译、Android resource/manifest、
   source/test contract。
4. 只修复当前 Batch 2 引入或暴露的具体问题；每次先跑最小失败任务，再回归完整编译。
5. 每个失败与修复追加到新的 Batch 2 build 记录，不覆盖旧失败事实。

### Stage 2 — 自动化构建与测试门禁

先用 `./gradlew :android:tasks --all` 和根项目 task 列表确认当前 checkout 的精确 task
名称，再依次完成并保存日志：

1. adapter truth-table 与 negative-inference unit tests；
2. `:android:testDebugUnitTest`；
3. `:android:lintDebug`；
4. debug APK assembly；
5. androidTest APK assembly；
6. release manifest；
7. release assembly；
8. Desktop fallback test 与 `desktopTest`；
9. release-source isolation、debug evidence Activity non-export/non-release packaging；
10. `git diff --check`、XML、资源名对齐、expect/actual 数量和 source-link bounds。

不因单个 task 已是 up-to-date 就跳过必要的 clean-room 复核；也不得通过删除用户工作树
来获得 clean build。

### Stage 3 — API 28 真实设备门禁

1. 优先复用已安装的 API 28 system image；没有时只安装所需官方 image。
2. 新建或克隆本批专用 AVD，不删除或覆盖已有 AVD/snapshot。
3. 安装当前构建，执行 clean cold launch。
4. 证明 unchanged v6.5.6 receiver/server/core 启动。
5. 进入生产 P08 可达路径，核对 loading、true empty、network unknown/device offline、
   core stopped/unavailable 等适用状态。
6. 保存设备信息、APK hash、安装命令、Logcat、UI tree、测试报告和关键截图。

### Stage 4 — API 35 升级与真实 P07 门禁

1. 使用本批专用 API 35 AVD，不改写 Foundation 的旧设备证据。
2. 先用相同 suffix/signing 的官方 baseline 建立合成非空用户/聊天数据。
3. 记录升级前数据库、preferences 和允许声明的文件 hash。
4. same-package 覆盖安装当前 Nome build，不清数据。
5. 证明 receiver/core 冷启动、当前身份正确、非空 P07 production route 可达。
6. 核对会话顺序、名称、摘要隐私、时间、favorite、unread、pending deletion、
   unavailable cached rows、core stopped read-only 和 navigation guards。
7. 只对实际取证的文件作 byte-identical 声明，不扩大到未核验数据库。
8. 保存升级、真实 core、UI tree、Logcat、测试报告和截图证据。

### Stage 5 — 网络、停止/启动与代际真值

1. 用平台 airplane/offline 切换证明 `Unknown`、`Online`、`DeviceOffline`；
2. 不把 device connectivity 推断为 relay/server/global health；
3. 用官方 core stop/start 路径验证 cached rows 与操作禁用；
4. 验证 same-generation refresh 不隐藏缓存行；
5. 验证 user/host generation change 隐藏旧身份行；
6. 验证 cancellation 继续传播，不被映射成 ordinary unavailable。

### Stage 8 — 证据冻结与两轮正式复核

只有 source、测试、截图、文档和证据都稳定后：

1. 更新本批 README、build verification、state truth table、threat-model delta；
2. 新增并核验 API 28/API 35、升级、comparison、reports 等计划要求的证据；
3. 重跑旧 Phase 1/Foundation hashes，证明未被修改；
4. 冻结 `REVIEW_INPUT_SHA256SUMS`；
5. 对同一 digest 连续执行两轮独立、完整复核；
6. 任一轮发现问题：修复后重新冻结 digest，并从 Round 1 重新开始；
7. 两轮均为 ZERO ISSUES 后，生成最终 `SHA256SUMS`；
8. 最后再次核验 Git baseline、dirty tree、forbidden paths、staged/commit/push 状态。

两轮复核至少覆盖：

- correctness 与状态真值；
- stale generation / cancellation / failure-vs-empty；

- navigation、pending-deletion 和 core-stopped guards；
- Android/Desktop/release source isolation；
- 双语、明暗、200%、48dp、TalkBack；
- 文档/source anchors；
- 证据声明是否超过实际证明范围。

## 7. 允许的故障处理

- Gradle/SDK/AVD 缺失：优先使用当前机器官方 Android Studio/SDK；必要时安装缺失的官方
  platform/system image，不迁移或删除现有用户 AVD。
- 编译/测试失败：定位最小根因，使用小 diff 修复，随后重跑最小任务和全量门禁。
- 设备不稳定：保存日志，冷启复现，必要时新建本批 namespaced AVD，不覆盖历史证据。
- 截图测试失败：区分产品 bug、测试 harness bug、设备时区/locale/font 配置；不通过手工
  改 PNG 制造 PASS。
- 需要越过第 4、5 节边界：停止 source 扩张，记录阻塞，不擅自增加 root/filter/core
  范围。
